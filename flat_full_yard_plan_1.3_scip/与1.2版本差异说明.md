# flat_full_yard_plan_1.3_scip 与 flat_full_yard_plan_1.2_scip 差异说明

本文对比 `flat_full_yard_plan_1.3_scip` 相比 `flat_full_yard_plan_1.2_scip` 的主要变化，重点说明业务流程、算法模块、输入输出和代码结构的差异。

## 总览

`flat_full_yard_plan_1.2_scip` 的全流程是：

```text
InputAdapterGd JSON
  -> 大计划 SCIP
  -> 中小计划 SA + 启发式小计划
  -> medium_plan.csv / small_plan.csv
```

`flat_full_yard_plan_1.3_scip` 的全流程是：

```text
InputAdapterGd JSON
  -> 大计划 SCIP
  -> 中小计划 SCIP 列生成
  -> medium_plan.csv / small_plan.csv
```

最核心的变化是：**中小计划求解器从模拟退火/启发式流程切换为 SCIP 列生成流程**。大计划求解器仍然是加权目标 SCIP/Gurobi 兼容求解器，但输入适配、诊断项和部分业务约束有所增强。

## 入口变化

### 1.2 版本入口

`flat_full_yard_plan_1.2_scip` 主要提供一个完整流程入口：

```powershell
python run_flat_full_yard_plan.py --adapter-json input_data.json --run-name object_input_full_check
```

全流程内置两段：

- 大计划：`planning_large_solver.solve_daily_rolling_yard_plan`
- 中小计划：`block_bay_planning.sa_solver.SimulatedAnnealingSolver`

中小计划相关参数主要是 SA 迭代、随机种子、小计划 proxy 检查频率等：

- `--medium-iterations`
- `--medium-seed`
- `--energy-record-every`
- `--small-plan-proxy-height-capacity-penalty`
- `--small-plan-proxy-every`

### 1.3 版本入口

`flat_full_yard_plan_1.3_scip` 提供四个运行入口：

| 入口 | 作用 |
| --- | --- |
| `run_flat_full_yard_plan.py` | 完整大中小计划流程 |
| `run_large_plan.py` | 只运行大计划 |
| `run_medium_small_column_generation.py` | 给定外部大计划，只运行中小计划列生成 |
| `run_small_plan_from_medium.py` | 给定外部中计划，只运行小计划 |

完整流程入口仍然是：

```powershell
python run_flat_full_yard_plan.py --adapter-json input_data.json --run-name full_check
```

单独大计划入口：

```powershell
python run_large_plan.py --adapter-json input_data.json --run-name large_only
```

单独中小计划入口：

```powershell
python run_medium_small_column_generation.py `
  --adapter-json input_data.json `
  --big-plan path\to\allocation.csv `
  --run-name medium_small_only
```

单独小计划入口：

```powershell
python run_small_plan_from_medium.py `
  --adapter-json input_data.json `
  --medium-plan path\to\medium_plan.csv `
  --big-plan path\to\allocation.csv `
  --run-name small_only
```

`--big-plan` 在单独小计划入口中是可选的；不提供时，会从外部 `medium_plan.csv` 汇总推导小计划使用的大计划配额。

## 中小计划算法变化

### 1.2 版本：SA + 启发式小计划

1.2 版本保留本地 SA 求解器：

- `block_bay_planning/area_plan_solver.py`
- `block_bay_planning/sa_solver.py`

业务逻辑是：

1. 中计划先按粗属性组分配到箱区。
2. SA 通过迭代搜索改善中计划目标。
3. 小计划在中计划结果之后用构造式启发式落到贝位。
4. SA 过程中用 small-plan proxy 估计后续小计划质量。

典型输出包括：

- `medium_plan.csv`
- `small_plan.csv`
- `small_plan_six_bay_blocks.csv`
- `energy_convergence.csv`
- `diagnostics.json`

`energy_convergence.csv` 用于观察 SA 能量收敛。

### 1.3 版本：SCIP 列生成

1.3 版本移除了本地 SA 中小计划求解器，新增列生成求解器：

- `column_generation_planner.py`
- `medium_small_column_generation_bridge.py`
- `small_plan_from_medium.py`

业务逻辑是：

1. 生成“细属性组/预测兜底组 - 贝位 - 箱量”的候选列。
2. 受限主问题选择候选列。
3. 列生成 LP 根据对偶价格继续补充列。
4. stage0 先确定最少未放置箱上限。
5. diving 将 LP 解转成整数方案。
6. staged greedy repair 按 stage1a、stage1b、stage2、stage3 补齐未放置箱。
7. repair LNS 在局部释放一批细属性组，尝试改善未放置箱、集中性和继承性。

列生成版本的主要目标是：

- 细属性组贝位集中。
- 粗属性组箱区集中。
- 大计划继承。
- 容量、尺寸、配额和混放规则作为硬约束控制可行性。

列生成版本输出新增：

- `generated_columns.csv`
- 更丰富的 `diagnostics.json`
- `master_status`
- `stage0_unplaced_cap`
- `repair_lns_rounds_run`
- `inheritance_ratio`
- 粗属性组碎片诊断等

`energy_convergence.csv` 不再是主输出，因为中小计划不再使用 SA 迭代能量曲线。

## 中小计划阶段含义

1.3 版本的 repair 阶段包含四个业务放宽层级：

| 阶段 | 含义 |
| --- | --- |
| stage0 | 在大计划精确箱区配额内做主分配，并确定未放置箱上限 |
| stage1a | repair 中继续使用精确大计划箱区配额补箱 |
| stage1b | 放宽到同航次、同流向的大计划覆盖箱区 |
| stage2 | 放宽到任意大计划覆盖箱区 |
| stage3 | 放宽到功能兼容的箱区兜底补箱 |

这些阶段放宽的是候选箱区范围和大计划精确配额，不放宽容量、尺寸、混放、TOPS、箱区功能等物理和业务硬约束。

## 外部中计划小计划入口

1.3 版本新增 `run_small_plan_from_medium.py`，用于外部已经给定中计划时，只生成小计划。

外部中计划会形成硬约束：

- 粗属性组 + 箱区配额
- 如果有 `bay_key` 或 `bay_no`，还会形成粗属性组 + 箱区 + 贝位配额

该入口固定使用 `doc-only` 口径，只规划当前未进场资料箱，不生成预测兜底组。

## 输入链路变化

### 标准输入对象

两个版本都使用 `InputAdapterGd` JSON 作为标准输入，并且主流程不会把 JSON 还原成 `parquet/xlsx/csv` 临时目录。

1.3 版本进一步明确了对象传递边界：

- 完整流程中，大计划求解后直接用内存中的 allocation rows 构造中小计划输入。
- 单独中小计划中，标准输入仍然先还原为 `InputAdapterGd` 对象；外部大计划 CSV 只作为大计划边界输入。
- 单独小计划中，标准输入仍然先还原为 `InputAdapterGd` 对象；外部中计划 CSV 和可选外部大计划 CSV 作为外部计划边界输入。

也就是说，1.3 版本后续中小计划流程不再把标准输入 JSON 路径当作数据目录反复读取。

## 大计划模块变化

大计划求解器主体仍是 `planning_large_solver.py`，但 1.3 版本增加或强化了若干业务控制和诊断。

### 用户指定箱区控制

1.3 版本在输入适配层支持：

- `user_design`
- `user_design_large_plan_area`
- `adjust_plan_info.large_plan.add`
- `adjust_plan_info.large_plan.remove`

这些信息会形成：

- 航次可用箱区 allowlist
- 航次禁用箱区 blocklist
- 人工 add 箱区 required area

大计划模型中 required area 未使用会产生软惩罚，诊断中会记录：

- `user_design_active`
- `user_design_large_plan_area`
- `required_area_unmet`

### 近靠泊冲突

1.3 版本新增近靠泊出口航次共用箱区惩罚。输入适配层按靠泊时间差构造 close berth conflict pairs，大计划目标中增加：

- `berth_conflict`
- `berth_conflict_shared`

终端和诊断中会输出：

- `close_berth_conflict_pairs`

### 离泊作业扣减

1.3 版本在输入适配层计算当前仍在场、但预计离泊释放的箱区作业扣减，用于更合理地估计箱区作业能力。诊断字段包括：

- `departure_operation_deduction_total`
- active export voyage area counts 等明细

### 可视化容错

1.2 版本直接导入并调用 `planning_large_visualize.generate_yard_visualization`。

1.3 版本对 `PIL/Pillow` 缺失做了容错：

- 缺少可视化依赖时跳过可视化。
- 大计划和全流程求解仍继续。
- `pipeline_summary.json` 中记录 skipped reason。

## 堆场与中小计划数据模型变化

1.3 版本的 `block_bay_planning/models.py` 和 `data_loader.py` 增强了排级/属性规则字段。

新增或强化的典型字段：

- `AttributeRules`
- `bay_no_mix_attributes`
- `row_no_mix_attributes`
- `Bay.row_cap_by_size`
- `Bay.row_physical_capacity`
- `Bay.large_bay_partner_key`
- `Bay.existing_attrs`
- `Bay.existing_attrs_by_row`
- `ProblemData.attribute_rules`
- `ProblemData.user_voyage_area_allowlist`
- `ProblemData.user_voyage_area_blocklist`
- `ProblemData.user_voyage_area_requirements`

这些字段让列生成器可以更严格地控制：

- 20/40/45 尺寸容量。
- 40/45 大贝 footprint。
- 同贝位不混尺寸/箱高。
- 同排不混卸港等属性。
- 用户指定箱区策略。

## 输出变化

### 完整流程输出

两个版本都输出：

- `outputs_large/latest_run/allocation.csv`
- `outputs_large/latest_run/allocation_new.csv`
- `outputs_large/latest_run/diagnostics.json`
- `medium_small_plan/medium_plan.csv`
- `medium_small_plan/small_plan.csv`
- `medium_small_plan/small_plan_six_bay_blocks.csv`
- `medium_small_plan/medium_demand_by_port.csv`
- `medium_small_plan/big_plan_used.csv`
- `medium_small_plan/diagnostics.json`
- `pipeline_summary.json`

1.3 版本新增：

- `medium_small_plan/generated_columns.csv`

1.2 版本特有：

- `medium_small_plan/energy_convergence.csv`

### pipeline_summary 差异

1.2 版本的中小计划摘要偏 SA：

- `medium_energy`
- `medium_row_count`
- `small_row_count`

1.3 版本的中小计划摘要偏列生成：

- `medium_algorithm`
- `medium_master_status`
- `medium_unplaced_boxes`
- `large_allocation_used_by_medium_small = in_memory_large_solution`

## 结果理解上的差异

### 1.2 版本

中小计划结果主要从 SA 能量、收敛曲线和启发式落贝结果判断。小计划可行性更多依赖后处理构造和 proxy 质量。

### 1.3 版本

中小计划结果主要从列生成诊断判断：

- `unplaced_boxes`：是否仍有未放置箱。
- `stage0_unplaced_cap`：stage0 证明或采用的未放置箱上限。
- `master_status`：列生成/diving 主问题状态。
- `final_column_count`：最终列池规模。
- `medium_big_plan_inheritance.inheritance_ratio`：大计划继承率。
- `medium_fragmentation`：粗属性组箱区碎片情况。
- `small_medium_consistency_violations`：小计划汇总是否超过中计划口径。

## 迁移影响

### 使用方式

如果只跑完整流程，命令基本保持不变：

```powershell
python run_flat_full_yard_plan.py --adapter-json input_data.json --run-name full_check
```

但中小计划参数需要从 SA 参数切换到列生成参数。

### 输出消费

下游如果依赖 `energy_convergence.csv`，需要改为读取 `diagnostics.json` 中的列生成诊断字段。

下游如果需要分析列生成过程，可以读取新增的 `generated_columns.csv`。

### 单独调试

1.3 版本更适合拆分调试：

- 大计划异常：单独跑 `run_large_plan.py`。
- 中小计划异常：用已知 `allocation.csv` 跑 `run_medium_small_column_generation.py`。
- 小计划异常：用已知 `medium_plan.csv` 跑 `run_small_plan_from_medium.py`。

## 一句话总结

`flat_full_yard_plan_1.3_scip` 保留了 1.2 版本的对象化标准输入和大计划求解框架，但把中小计划核心从“SA 中计划 + 启发式小计划”升级为“SCIP 列生成 + diving + staged repair + LNS”，并补齐了单独大计划、单独中小计划、单独小计划入口。整体更强调硬约束下的可解释求解、可拆分验证、粗细属性集中性和大计划继承诊断。
